## OWNER ACTION: permiso de Actions en el token de GitHub

El contrato del programa (Hard Cap A / punto #12 de los defectos
conocidos) exige dos ejecuciones completas verdes de CI sobre el mismo SHA
final de `main`. Sólo existe una (run 504). Se intentó cerrar la brecha sin
tocar código:

- `actions_run_trigger` método `run_workflow` sobre `ci.yml` en `main` →
  `403 Resource not accessible by integration`.
- `actions_run_trigger` método `rerun_workflow_run` → mismo `403`.

El token del integrador (GitHub App vía MCP) no tiene alcance de escritura
sobre Actions. No hay forma de rodear esto sin violar una regla explícita
del programa (nunca commit vacío ni cierre/reapertura de PR para forzar
CI). **`OWNER ACTION: PERMISO DE ACTIONS`** — el titular necesita, o bien
conceder `actions: write` a la integración, o volver a ejecutar
manualmente el run 504 (o cualquier run sobre `51538db`) desde la UI de
GitHub. Mientras tanto, el hard cap A queda con evidencia parcial (1 de 2
corridas) y se declara así, no se esconde.

## En curso al cerrar esta nota — evidencia de estrés denso a 100k

`modify.dense-stress` (1 pt, `docs/competitive/rubric.json`) exige el
artefacto versionado `docs/cad/evidence/cad-dense-editing-100k.json`, que
NO existe en el árbol — el generador
(`scripts/cad/dense-editing-evidence.mjs`) existe pero nunca se corrió
hasta publicar. Antes de comprometer tiempo de sesión a esto, se corrió
una sonda de calibración (`CAD_DENSE_REPEATS=1`, un solo proceso) para
medir el coste real en esta máquina (Xeon 2.10 GHz, 4 hilos lógicos, 15,7
GB RAM, SwiftShader — sin GPU):

| Gesto | Mediana (REPEATS=1) |
| --- | --- |
| abrir paleta de selección | 38,77 s |
| seleccionar TODO (100k) | 26,99 s |
| mover grupo masivo | 8,22 s |
| deshacer movimiento masivo | 9,95 s |
| borrar capa completa | 7,35 s |
| deshacer borrado | 10,08 s |
| ventana pequeña | 65,24 s |
| ventana grande | 65,71 s |
| crossing grande | 65,14 s |
| lazo | 200,55 s |
| pick + grips | 6,88 s |

Consistente con los números sueltos que la campaña COMMERCIAL-RC1 ya había
reportado en prosa (`CAMPANA_COMMERCIAL_RC1_20260826.md`: "paleta 32-43 s",
"lazo 187-198 s" a 100k SwiftShader) — la sonda no es una sorpresa, es la
confirmación de que la metodología del arnés mide lo mismo que ya se sabía
sin dejar el artefacto que la rúbrica exige.

**El problema es de escala, no de honestidad:** una sola corrida a
REPEATS=1 tardó **2.388 s (39,8 min)** de punta a punta. El generador de
evidencia exige "mediana de TRES corridas en procesos separados" con el
REPEATS por defecto (3, para poder promediar dentro de cada corrida) — la
regla propia del repositorio, no algo que esta sesión pueda relajar con
`--min-runs` sin fabricar evidencia más débil de la que el criterio pide.
Con REPEATS=3 cada corrida puede acercarse a la hora; tres corridas
separadas caen en el orden de 2–3 horas de reloj.

Se lanzó la corrida 1 de 3 (`CAD_DENSE_REPEATS` por defecto = 3) en
segundo plano; **estado y resultado exactos en la sección "Siguiente
unidad exacta" al pie**, actualizada al cerrar esta sesión. No se commitea
ningún artefacto parcial ni con menos de 3 corridas — el archivo o cumple
la regla completa del generador, o no se publica.
